This is how a company rolls Blindsight Endpoint out "like AD": one silent
push from the MDM, the directory auto-provisions every employee, and
every device binds to a real identity.

There are two independent axes; you almost always want both.

1. **Fleet software push.** IT deploys the agent to every machine
   with no per-user clicks. Windows: `.msi` via Intune, GPO, or SCCM,
   with one workspace‑wide enrollment token baked into the command;
   the agent self‑enrolls on first run. macOS: the `.dmg`, which
   carries no token; each Mac enrols when its user signs in.
2. **Directory sync + SSO.** Your IdP (Entra, Okta, Google) provisions
   every employee into the workspace (SCIM) and binds each device to
   the matching directory user on first sign‑in (OIDC).

On Windows these are decoupled on purpose. The silent installer runs
as SYSTEM and cannot know the human user, so identity is bound
**after** enrollment via the SSO device‑code flow, opened
automatically by the agent. On macOS the two happen together: the
sign-in that binds the identity is the one that enrols the device.
Either way, the employee signs in once.

See [Identity binding](/endpoint/identity) for the directory and SSO side,
and [Installing the agent](/endpoint/install) for what an install changes on
a single machine. This page is the IT‑side rollout.

## 1. Create the fleet enrollment token

<Steps>
  <Step title="Open Endpoint → Devices">
    **Endpoint → Devices → create token.** The copy-paste install command
    with the token already baked in is on
    **Endpoint → Configurations → Install**.
  </Step>
  <Step title="Copy the token">
    Shown when it is minted. Store it in your MDM secret vault. One
    token covers the entire Windows fleet. Macs do not use it. An admin
    who holds `endpoint.enrollment.reveal` can show it again later, so
    an MDM job can reuse it without minting another.
  </Step>
  <Step title="(Optional) Restrict the token">
    Token settings let you cap the number of activations, set an
    expiry, and limit it to a specific directory group.
  </Step>
</Steps>

## 2a. Windows push

Windows is the primary platform. The agent runs as a SYSTEM service
named `BlindsightDLP`.

```text
msiexec /i Blindsight-<version>.msi /qn ^
  CLOUD_BASE=https://api.blindsight.example.com ^
  ENROLL_TOKEN=antde_xxxxxxxxxxxxxxxxxxxx
```

`CLOUD_BASE` and `ENROLL_TOKEN` are the **only two** properties the
package takes. Both are 64‑bit, per‑machine, x64 only.

Deploy via:

- **Intune** as a Win32 app. See [Deploying with Intune](#deploying-with-intune).
- **Group Policy** as a startup script. See [Deploying with Group Policy](#deploying-with-group-policy).
- **Configuration Manager (SCCM)** and other tools. See [Configuration Manager and other tools](#configuration-manager-and-other-tools).

The MSI writes `HKLM\SOFTWARE\Blindsight` (`CloudBaseURL`,
`EnrollmentToken`, `SSOLoginBase`), generates a **per-machine**
inspection root CA and adds it to the machine trust store (there is no
shared fleet key), and installs the SYSTEM service. The service self‑enrolls and runs the SSO
identity‑binding flow. An interactive install opens the dashboard
once; `/qn` stays silent.

<Note>
  Passing a property on the command line always wins. If you omit
  both, the installer keeps whatever the machine already has in
  `HKLM\SOFTWARE\Blindsight`, and only a genuinely fresh install
  falls back to the build's default. This is what makes an upgrade
  safe: a self-update runs `msiexec` with no properties and must not
  retarget a device that IT pointed somewhere specific.
</Note>

<Warning>
  A bare `msiexec /i Blindsight-<version>.msi /qn` does **not** enrol a device
  unless the build was created with a token baked in, or the machine
  already carries one. Pass `ENROLL_TOKEN` for a fleet push.
</Warning>

<Warning>
  The per‑user `.exe` installer (Inno Setup) has been **withdrawn** and
  should not be used for new installs, fleet or otherwise. It installs
  into the user profile, which leaves the device token and the local
  policy owned by the person the agent is protecting, so the tamper
  resistance the MSI gets from LocalSystem does not apply. It is also a
  separate product identity, so `msiexec` cannot upgrade it in place.
</Warning>

On Windows 11 the stock vulnerable-driver blocklist refuses the
bundled capture driver and the agent falls back to its explicit-proxy
engine, which covers less. This is expected and needs no action from
you, but it does change coverage. See
[Windows 11 and the network driver](/endpoint/install) for what is and is
not covered, and how the device reports it.

## Deploying with Intune

This is the configuration that enrolled a test fleet of Windows
machines cleanly and silently, with no sign-in and no reboot. The install
ran as SYSTEM and finished in under a minute. A machine that installed
during boot, before anyone signed in, enrolled about a minute later. It
was validated on Windows Server 2022 and Windows Server 2025.

### Pick how to build the app

There are two ways to build the app. They end in the same Intune app.

- **The ready-made package.** In **Install → Windows → Intune**, download the
  `.intunewin` file. It holds the MSI, `install.cmd`, `uninstall.cmd` and a
  file with the enrollment token. You upload it to Intune and copy the
  settings from the checklist the console shows beside it. The token is in the
  package, never in the install command.
- **By hand.** Package the MSI and `uninstall.cmd` yourself. The steps below
  show this way.

Connect Intune is separate. It does not build the app. It shows how far the
rollout has got and can deploy the agent to a group. See
[Connect Intune](#connect-intune).

### Create the app

The console walks through these same steps one at a time: open
**Endpoint → Configurations → Install**, choose **Windows**, then **Intune**.
It shows the install command with a **Generate token** button, so the
command you copy already holds a token.

<Steps>
  <Step title="Package the MSI">
    From **Endpoint → Configurations → Install**, download
    `Blindsight-<version>.msi` (**Download MSI**) and the install kit
    (**Download kit**). Put the MSI and the kit's `uninstall.cmd` in one
    folder and package it with the Microsoft Win32 Content Prep Tool
    (`IntuneWinAppUtil.exe`). Set the setup file to the MSI. Add it to
    Intune as a **Windows app (Win32)**, with **Install behavior** set to
    **System** and the architecture set to **x64**.
  </Step>

  <Step title="Set the install command">
    On the **Install** step, select **Generate token**. The console puts the
    token into the command and shows it once, so copy the command before you
    leave the page.

    ```text
    msiexec /i Blindsight-<version>.msi CLOUD_BASE="https://api.blindsight.example.com" ENROLL_TOKEN="antde_xxxxxxxxxxxxxxxxxxxx" /qn /norestart
    ```

    This command was validated running as SYSTEM in a 32-bit process, which
    is how Intune runs it.

    <Warning>
      The file name in the command must match the MSI inside your
      `.intunewin` package, letter for letter. Each release is named after
      its version, so a package built from an earlier download holds an
      older name. If the command names a file the package does not hold,
      `msiexec` fails with 1619 and Intune reports `0x80070653`. In the
      console, type your packaged file name into **MSI file in your package**
      and the command follows it.
    </Warning>

    The agent updates itself after it installs, so the packaged version can
    stay old. You do not need to rebuild the package for every release.
  </Step>

  <Step title="Set the detection rule">
    Add a rule manually, with rule type **File**:

    | Field | Value |
    | ----- | ----- |
    | Path | `C:\Program Files\Blindsight` |
    | File or folder | `BlindsightAgent.exe` |
    | Detection method | File or folder exists |
    | Associated with a 32-bit app on 64-bit clients | No |

    The agent updates itself and keeps this file, so the rule keeps working
    after an update. Never detect on the ProductCode. An update installs a
    new ProductCode, so a rule that pins it starts reporting "not detected"
    within minutes of the first update, and Intune's built-in MSI rule pins
    it.

    You can also detect on the UpgradeCode
    `{1B8032BE-2978-4F43-802A-3A10B186515F}` with no script. Add a rule of
    type **Registry**, with key
    `HKEY_LOCAL_MACHINE\SOFTWARE\Classes\Installer\UpgradeCodes\EB2308B1879234F408A2A3011B6815F5`,
    detection method **Key exists**, and **Associated with a 32-bit app on
    64-bit clients** set to **No**. The kit's `detect.ps1` does the same with a
    script.

    Use the File or the Registry rule, not `detect.ps1`. Under the PowerShell
    execution policy **AllSigned**, Intune cannot run `detect.ps1` at all: it is
    unsigned, and the policy refuses it even with `-ExecutionPolicy Bypass`, in
    32-bit and 64-bit alike. The two rules above need no script and are not
    affected by AllSigned. Both were
    checked on a machine under AllSigned: the key exists exactly while the agent
    is installed, and it survives an update.
  </Step>

  <Step title="Set the uninstall command">
    The ProductCode changes with every version, so the uninstall command runs
    the kit's script, which finds the installed product through the
    UpgradeCode:

    ```text
    uninstall.cmd
    ```

    `uninstall.cmd` has to be inside the `.intunewin` package. If you leave
    it out, uninstalling from Intune fails. It is a plain cmd file, so it runs
    where PowerShell is locked down. It treats `1605` (the product is already
    gone) as success. When uninstall codes are required on the workspace,
    authorize the devices first: in **Endpoint → Devices**, select them and
    choose **Authorize removal**. Do not put an uninstall code in the Intune
    uninstall command. Intune stores the command in plain sight and logs it on
    every device. For a one-off manual or RMM run you can pass the code as the
    first argument: `uninstall.cmd <code>`. See
    [Uninstalling the agent](/endpoint/uninstall).
  </Step>

  <Step title="Leave the return codes at their defaults">
    `0` and `1707` are success, `3010` is a soft reboot, `1641` a hard
    reboot, and `1618` retries. Expect `1603` for a downgrade, or when the
    workspace requires an uninstall code and none was given. A re-run of a
    failed install, with a corrected token or address, enrolls normally.
  </Step>

  <Step title="Add the refused-token return code (ready-made package)">
    The ready-made package's `install.cmd` does not stop at the installer. After
    `msiexec` returns `0` it waits up to 120 seconds for the agent to say
    whether it enrolled. If the platform refused the token because it is
    expired, revoked or unknown, `install.cmd` exits with `7001`. Add this
    return code in Intune:

    | Return code | Type | Meaning |
    | ----------- | ---- | ------- |
    | `7001` | Failed | Enrolment token refused: build a new package |

    The checklist next to the download lists it. Without it the install would
    read **Installed** on a device that never enrolled. An agent that is too old
    to say, or one that has not decided in 120 seconds, leaves the result at
    `0` after the full wait, so the install takes up to two minutes longer
    than the installer alone. The kit's `install.bat` does the same and exits `7001`.
    Revoke the old token and build a new package.

    A device that is already enrolled does not wait: the script sees that and
    exits `0` at once. Any other `msiexec` failure code (`1603`, `1618`,
    `1619`) passes straight through without the wait.
  </Step>

  <Step title="Assign it to a device group">
    Target **devices**, not users. The install needs no one signed in.
    For a pilot, scope the assignment to one group and use a token
    limited to the matching directory group. See the pilot workflow
    below.
  </Step>
</Steps>

### Package the kit instead

If you prefer scripts to a bare MSI, package the whole kit folder with the
MSI and set the setup file to `install.bat`. It is plain cmd, so it runs
where PowerShell is locked down (AllSigned, constrained language mode). It
carries the token and exits with `msiexec`'s own exit code, so Intune reads
the result correctly. It names the MSI file the kit was built for, so
package the MSI under that exact name; the agent updates itself afterwards,
so the packaged version can stay old.

| Field | Value |
| ----- | ----- |
| Install command | `install.bat` |
| Uninstall command | `uninstall.cmd` |
| Detection | The File or the Registry rule above. No detection script. |

The kit also holds `install.ps1` and `detect.ps1` for fleets that run
unsigned PowerShell. Under AllSigned they are refused, so the console and
the `README.txt` recommend `install.bat` and the File or Registry rule. The
kit's `README.txt` lists the same fields, and both are generated from one
place, so the console and the README always agree. The kit holds a live
enrollment token in `install.bat` and `install.ps1`, so treat the zip as a
secret.

### Updates

The agent keeps itself up to date, so leave **auto-update** on and detect
by the UpgradeCode or file version. If Intune must be the only thing that
changes the version, set the machine environment variable
`BLINDSIGHT_AUTO_UPDATE=0` before the install. The service reads it only
after a reboot.

An upgrade restarts the service, and during the restart the device is
not inspected for roughly 40 to 55 seconds, with the posture reading
`bypassed` until it restores. Schedule updates accordingly.

### Tokens

- Use a separate named kit, and therefore a separate token, for each wave
  of devices.
- Revoke an old token only after every device enrolled with it is stable.
- Do not turn on verbose Windows Installer logging (`/l*v`) on a
  production fleet. A verbose log records the install command line. If a
  token reaches a log, revoke it and mint another.

### Golden images

Always run **sysprep** on an image before you clone it. Two machines
cloned without it share one machine identity and merge into one device
row. The agents then swap the token between them every few minutes and the
posture stays `bypassed`. The row shows **Shared machine identity**, and an
audit record, "Two machines are enrolling as one device", is written once.
This holds when the clones keep the same host name too. Machines cloned
with sysprep get their own identities and their own rows. If you find a row
like this, sysprep the image and re-install the agent on the clones. Allow
re-enrollment before you revoke the row, or the machine that kept it cannot
enrol again.

### What shows up in the console

- **Identity is `pending` on every Windows device.** The service runs as
  SYSTEM, so it reports the machine account (`HOST$`) as the device's
  operating system user and never learns who signs in. The devices are
  fully protected while they are pending. To attribute traffic to a
  person, bind each device through
  [single sign-on](/endpoint/identity), or
  an admin chooses **Confirm owner**. A confirmation is lost on a clean
  re-enrolment, so it has to be made again after a reinstall.
- **A device appears when it first enrolls.** There is no expected-versus-
  enrolled count. A machine that never enrolled is not in the console, so
  check Intune for its install status. `1603`, `1618`, `1605` and "not
  detected" are all visible only in Intune.
- **An offline machine installs and then enrolls.** The install returns
  `0` and the agent retries until it can reach the platform, typically
  within a few minutes of the network returning, including after a reboot
  while offline.
- **A bad token or address leaves no row.** The device log shows `401`, an
  unresolvable host, or a `405` for a wrong path. Rerun the install with
  the right values.
- **Seats.** At the seat limit, a new device gets `429` and no row. Free a
  seat by revoking a row in **Endpoint → Devices**.
- **A device that stops reporting** shows as offline after about five
  minutes, but its status stays `active` and its posture `protected`
  until you act. Nothing is raised for it.

### Device installation restrictions

Whole-device protection on Windows runs through a small network adapter, the
Wintun virtual adapter, which Windows installs the first time the lane starts.
If your Intune or Group Policy settings restrict which devices Windows may
install, allow this one. Without it, the agent keeps protecting browsers and
apps that use the system proxy, and the device row reads **Device
installation is blocked by policy**. The agent stops retrying and looks
again when the policy changes, or after an hour.

Allow one of these, narrowest first:

| Policy setting | Value |
| --- | --- |
| Allow installation of devices that match any of these device IDs | `Wintun` |
| Allow installation of devices using drivers that match these device setup classes | `{4d36e972-e325-11ce-bfc1-08002be10318}` (Net) |

In Intune these are the **System → Device Installation → Device Installation
Restrictions** settings in the settings catalog or the administrative templates. If **Prevent installation of devices not
described by other policy settings** is on, one of the two allow rules above
is required. If a **Prevent installation of devices that match any of these
device IDs** or **setup classes** rule would match `Wintun` or the Net class,
add an exception for it. Rules for other adapters, such as GlobalProtect or a
VPN client, are not affected and the agent never touches those adapters.

The device's diagnostics bundle shows which restriction keys Windows read
and the Windows log lines for this device, under `network/`.

### Locked-down PowerShell and App Control

The ready-made package and the kit's `uninstall.cmd` and `install.bat` are
plain cmd files. They run where PowerShell is locked down.

- **AllSigned.** When Group Policy sets this policy, it refuses an unsigned
  `.ps1` even with `-ExecutionPolicy Bypass`. The kit's `install.ps1` and `detect.ps1` are
  unsigned, and Blindsight cannot sign them for you. Use `install.bat` or the
  package, the File or Registry detection rule, and `uninstall.cmd`. Or sign
  the scripts with your own certificate.
- **Constrained language mode.** App Control script enforcement turns it on.
  Scripts that create COM objects fail in it. The kit's scripts use none.
  Test one device first, because an install under constrained language mode
  can still fail with `1603` on agent version 1.6.3.
- **App Control (WDAC) and AppLocker.** Allow the Blindsight publisher
  (`Blindsight Technologies AG`) at the **Publisher** or **FilePublisher** rule
  level. Never use a leaf certificate rule or a hash rule. The signing
  certificate is replaced every few days and the file hashes change with each
  release, so either one breaks at the next update. The agent also ships files
  signed by other vendors, and a publisher rule for the Blindsight name does
  not cover them. Without them an App Control install fails with `1603` within
  seconds (Windows logs CodeIntegrity event 3077 for the file it refused), or
  hangs and then fails. Allow each vendor below too, or add a path rule for
  `%ProgramFiles%\Blindsight\*` instead. Under AppLocker DLL rules the tray does
  not start for standard users without them. Protection by the service still
  runs in that case. The AppLocker default rules work.

  Allow each signer **and the certificate authority that issued it**. A
  vendor can sign different files under different authorities. A rule made
  from one Python Software Foundation file does not cover `libffi-8.dll`,
  which is signed under a different authority from the rest, and App Control
  refuses that one file. These are the ten signer and authority pairs on the
  agent files signed by other vendors, as of agent version 1.6.51:

  | Signer | Issuing authority | Files |
  | ------ | ----------------- | ----- |
  | Microsoft Corporation | Microsoft Code Signing PCA 2010 | 44 |
  | Microsoft Corporation | Microsoft Code Signing PCA 2011 | 5 |
  | Microsoft Corporation | Microsoft Code Signing PCA 2024 | 3 |
  | Microsoft Windows Software Compatibility Publisher | Microsoft Windows Third Party Component CA 2013 | 5 |
  | Python Software Foundation | Microsoft ID Verified Code Signing PCA 2021 | 24 |
  | Python Software Foundation | DigiCert Trusted G4 Code Signing RSA4096 SHA384 2021 CA1 | 1 (`libffi-8.dll`) |
  | WireGuard LLC | DigiCert EV Code Signing CA (SHA2) | 2 (`wintun.dll`) |
  | Ars Nova Systems | DigiCert EV Code Signing CA (SHA2) | 1 (`WinDivert32.sys`) |
  | The WinDivert signer (a name in non-Latin characters) | Sectigo Public Code Signing CA EV R36 | 1 (`WinDivert64.sys`) |
  | The WinDivert signer (same name) | Sectigo Public Code Signing Root R46 | 1 (`WinDivert64.sys`) |

  The list can change with a release. To be sure, build the rules from an
  installed agent instead of copying the table: scan
  `C:\Program Files\Blindsight` with `New-CIPolicy -Level Publisher` and read
  the signer and authority of every file, or run `Get-AuthenticodeSignature` on
  the files. Rules built from the Blindsight publisher plus these ten pairs, with
  no path rule, were enough for an install, an update and an uninstall on a
  machine with App Control enforced.
- **Controlled Folder Access.** Only matters if you add
  `C:\ProgramData\Blindsight` as a protected folder. Then add
  `BlindsightAgent.exe` to the allowed apps, or the install fails with `1603`.

### Firewalls, proxies and TLS inspection

**Outbound allow list.** If your firewall blocks outbound traffic by default,
allow these:

| What | Where |
| ---- | ----- |
| The agent program | `C:\Program Files\Blindsight\BlindsightAgent.exe`, outbound |
| The tray app | `C:\Program Files\Blindsight\Blindsight.exe`, outbound. It makes the person's sign-in call itself. |
| Your Blindsight cloud address | port 443 |
| The download host | `downloads.blindsight.io`, port 443 |

Without the `BlindsightAgent.exe` rule, whole-device protection stays down and the device row
reads "traffic into the tunnel is blocked (firewall rule, error 10013)". The
explicit-proxy fallback cannot inspect either, because the agent's own
traffic is blocked. After you add the rule the device comes up in about two
minutes.

**Proxy servers.** On agent version 1.6.3, enrolment, sign-in, updates and the
uninstall check connect directly. They do not use the machine proxy, a PAC file
or `HTTPS_PROXY`. Allow direct outbound port 443 to the two hosts above, or
the device cannot enrol. Browsers and apps that go through your proxy are
not affected.

**TLS inspection.** Exempt the Blindsight cloud address and the download host
from TLS inspection wherever your policy allows. A gateway whose root
certificate the machine trusts can read the agent's control-plane traffic. That
includes the device token, the policy, and the pause, revoke and uninstall
decisions, and a gateway can change them in transit. Platform-signed decisions
are planned. They would let the agent refuse a changed answer.

On agent version 1.6.3 the agent trusts only its bundled certificate
authorities for these two hosts. If your gateway re-signs that traffic,
enrolment fails with `CERTIFICATE_VERIFY_FAILED`. The next build accepts
inspector roots that are in the machine certificate store, so inspection will
then work. That does not remove the reason to exempt the hosts.
When the agent's own traffic goes through an inspector, the device page says so
and names the issuer. A device whose AI sites are sent around Blindsight by a
company proxy, or are re-signed by an issuer nobody trusts, reads as not
inspected, with the reason and what to do.

**A failed enrolment.** A device that cannot enrol can be left with a machine
proxy setting that points at a local port nothing listens on. Programs such as
`curl`, `git` and `npm` then fail on that machine. Restarting the Blindsight
service resets it. Fix the network path first, then rerun the install.

### Connect Intune

Connect Intune lets the console read your Intune tenant. It lists the managed
Windows and Mac devices, matches each to a Blindsight device, and shows which
ones do not have the agent yet. From there it can also deploy the agent to an
Intune group.

1. Open **Endpoint → Configurations → Intune** and select **Connect Intune**.
2. Sign in with an account from your tenant and approve the read access the
   console asks for. Your tenant's rules for app consent apply.
3. Wait for the first sync. It reads the device list every four hours. You can
   also start one from the console.

A device matches strongly by its Entra device ID or its serial number, and by
host name only when the name is unique on both sides. A device that Intune
manages and that has no Blindsight match reads **Missing**: it is in Intune and
not running Blindsight. **Not in Intune** is the other way round, a Blindsight
device that Intune does not list. Reading changes nothing in your tenant.

After you deploy the agent from Connect Intune to a group, the console shows
how far the rollout has got: how many devices are targeted, and how many are
installing, installed, failed in Intune, enrolled and protected. Enrolled and
Protected count the devices that enrolled with this deployment's token.
A device that was already enrolled and protected before the deployment, which
Intune lists and Blindsight already knows, is counted as **Already protected**
in the heading line ("6 devices targeted, 2 already protected") and reads
**Already protected** on its row. It is not counted as enrolled by the
deployment, and it is not left out. A device that was enrolled before but is
paused, offline or revoked is not counted as already protected. It reads as
Intune reports it.

### Retiring devices

Revoke the device row in **Endpoint → Devices**. That releases its seat
and ends its token.

An uninstall pushed from Intune tells the platform as the agent goes, when the
device can reach the platform at that moment. If it cannot, the row stays active
and the seat stays held, so revoke the row. When the notice arrives, the row
then reads **Uninstalled**, and the seat is freed once the machine has
been quiet for 30 minutes. A machine that keeps reporting keeps its seat.
This holds in every uninstall mode except **enforce**, where an uninstall
with no code is recorded as tamper. Under **enforce**, an authorized or
coded uninstall frees the seat and records the device as uninstalled. See
[Uninstall codes](/endpoint/uninstall#uninstall-codes).

An uninstall leaves one thing behind on purpose: the Windows port
exclusion for ports 47324 to 47327. It is harmless and a reinstall reuses
it. Do not treat it as a failed uninstall.

The uninstall mode takes about three minutes to apply after you change it,
and an uninstall attempted in that window can return `1603`. Retry it.

## Deploying with Group Policy

Use a computer startup script that runs the kit's `install.bat`. Startup
scripts run as SYSTEM before anyone signs in.

<Steps>
  <Step title="Stage the files">
    Put `install.bat` and `Blindsight-<version>.msi` together in a network
    share that only computer accounts can read. Give **Domain Computers**
    read access and remove **Authenticated Users**. Do not use the GPO's own
    **Startup** scripts folder or any other part of SYSVOL. Every domain user
    can read SYSVOL, and `install.bat` holds the enrollment token.
  </Step>
  <Step title="Add the startup script">
    In Group Policy Management, open the GPO and go to **Computer
    Configuration → Policies → Windows Settings → Scripts (Startup/Shutdown)
    → Startup**. Add `install.bat` by its share path, for example
    `\\server\share\install.bat`.
  </Step>
  <Step title="Skip devices that already have the agent">
    Startup scripts run at every boot, and reinstalling the same version over
    a running agent is not harmless. The kit's `install.bat` already starts
    with this line, so a device that has the agent is skipped:

    ```text
    if exist "%ProgramW6432%\Blindsight\BlindsightAgent.exe" exit /b 0
    ```

    `%ProgramW6432%` is the 64-bit Program Files folder in a 32-bit and a
    64-bit command shell alike. It also means `install.bat` does not upgrade
    an installed agent. A newer MSI on the share is skipped, and the agent
    updates itself.
  </Step>
  <Step title="Link the GPO">
    Link it to the OU that holds the computers. They install at the next
    restart, or run `gpupdate /force` and restart.
  </Step>
</Steps>

`install.bat` also suits fleets whose policy enforces the `AllSigned`
PowerShell execution policy, because it runs no unsigned script.

<Warning>
  Do not use **Group Policy Software Installation** (Computer
  Configuration → Policies → Software Settings) with the MSI alone. It
  cannot pass `CLOUD_BASE` or `ENROLL_TOKEN`, so it installs an agent that
  never enrols. The service stays stopped and the device never appears in
  the console. If you must use it, give it a transform (`.mst`) that sets both
  properties, and keep the transform on the same restricted share, because
  it holds the token.
</Warning>

## Configuration Manager and other tools

For Configuration Manager (SCCM), create an application or package with
`install.bat` and the MSI as its content. Set the install command to
`install.bat`, run it as the system account whether or not a user is signed
in, and detect by the file `C:\Program Files\Blindsight\BlindsightAgent.exe`
existing. For an RMM tool or a one-off install, run the `msiexec` command
from **Endpoint → Configurations → Install → Command line** from an
elevated prompt, with the MSI in the same folder.

## 2b. macOS push

macOS ships as a **`.dmg`**, one per processor
(`Blindsight-Mac-<version>-arm64.dmg` for Apple silicon,
`Blindsight-Mac-<version>-x86_64.dmg` for Intel). Drag
`Blindsight Mac.app` into Applications. macOS 11.0 is the minimum.
There is no `.pkg`. The app is signed and notarized, so it opens
without a Gatekeeper prompt.

There is no token to distribute for a Mac. Push the disk image, or the
app from it, with Jamf, Kandji or Intune, or let employees take it from
the console's Downloads page. On first open the person signs in with
their work account, which enrols the device and binds their identity,
then approves the inspection certificate and the protection service
when macOS asks.

**Endpoint → Configurations → Install** offers a macOS install kit: a
README with the download links, checksums and steps for both builds on
your release channel. It holds no secret and can be shared freely.

For a single-tenant or self-hosted platform, push a configuration
profile in the `dev.blindsight` preferences domain so the app talks to
your platform rather than the Blindsight cloud:

| Key            | Value                                        |
| -------------- | -------------------------------------------- |
| `CloudBaseURL` | `https://api.blindsight.example.com`         |
| `SSOLoginBase` | `<CloudBaseURL>/api/auth/sso`                |

A per-user profile is read before the device-wide one.

Interception on macOS uses an automatic proxy configuration (PAC) on
every network service plus a local inspection proxy, with the
inspection root CA in the login keychain and a root guardian daemon
that restores the configuration if it is disturbed. See
[What the install actually changes](/endpoint/install) for the full list.

<Note>
  A macOS build older than 1.0.29 reports its bundle version as
  `0.1.0` to Finder and to inventory tools, whatever the agent
  actually is. Read the version from **Endpoint → Devices** instead,
  which is reported by the agent itself.
</Note>

Linux is not supported.

## 2c. Keeping the fleet up to date

The agent self-updates by default: it checks a release manifest 60
seconds after start and then every 6 hours, verifies the download's
SHA-256 and size before installing it, and preserves device state
across the upgrade (enrollment, the CA, the pseudonymization vault, the
local event spool, sign-in and settings).

| Channel   | What it is                                     |
| --------- | ---------------------------------------------- |
| `auto`    | The default. Follows whatever platform the device is enrolled against. |
| `stable`  | Promoted production builds.                    |
| `staging` | Internal and pre-release builds. `beta` is an alias for this. |

<Warning>
  On a managed fleet, set `auto_update = false` (under `[update]` in
  the agent's config, or `BLINDSIGHT_AUTO_UPDATE=0`) and push builds
  through your MDM instead, so version rollout stays on your change
  calendar.
</Warning>

Never delete `%ProgramData%\Blindsight\pseudonym_vault.db` or
`vault.key`. They hold the only mapping from a surrogate back to what
the person actually wrote, and losing them is permanent and visible
to the user. A genuine uninstall wipes them; an upgrade does not. See
[Uninstalling the agent](/endpoint/uninstall).

## 3. Verify rollout

Open **Endpoint → Devices** in the dashboard. Each machine appears
with an **Identity** column.

| Identity status | What it means                                                              |
| --------------- | -------------------------------------------------------------------------- |
| `bound`         | The employee completed SSO. Traffic is attributed to a directory user.      |
| `auto`          | OS username matched a directory user via SCIM. Useful for non‑user devices. |
| `pending`       | Agent enrolled, identity binding not yet completed.                         |

Tamper attempts (uninstall blocked by guardian, modified binary,
disabled proxy) surface as high‑severity audit events under
`POST /agent/tamper-events`.

## Managed devices in the desktop app

The desktop app treats a device you provisioned differently from one a
person set up themselves, so a person cannot undo what you chose.

- **Sign-in options are hidden.** On a managed device the sign-in screen
  has no **Advanced** link for the workspace address, App ID and token,
  and the device refuses a change to the workspace address. A Mac counts
  as managed when an MDM configuration profile is present. A Windows
  device counts when the installer or policy sets the platform address
  or an enrolment token.
- **Start at Login stays on.** Where the machine starts the app at every
  sign-in, the **Start at Login** item is not offered, and an earlier
  choice of off is recorded as on so the app does start. That is a
  macOS MDM profile, or the machine-wide startup entry the Windows
  installer writes.

## Out-of-repo signing

Certain steps **cannot** be done inside Blindsight's source tree.
They require external certificates and Apple / Microsoft developer
relationships.

| Step                                                       | Why it cannot be done here                                                                          |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Signed WFP kernel driver (optional, admin‑tamper hardening)  | Needs EV cert + Microsoft attestation signing.                                                       |

Windows installers and binaries, and the macOS app and disk images, **are** signed in the shipped builds. The macOS builds are also notarized.

Talk to your account manager for the signed bundles tailored to your
organisation.

## SAML

SAML is schema‑ready in the backend but not enabled in this build.
OIDC covers Entra, Okta, Google, and Ping. Open a ticket if you have
a SAML‑only IdP.

## Common workflows

<AccordionGroup>
  <Accordion title="Pilot a small group before fleet rollout">
    1. Create a token in **Endpoint → Devices** restricted to one
       directory group (`engineering-pilot`).
    2. Push the agent to that group via your MDM's smart‑group
       scoping.
    3. Watch verdicts and tamper events for a week.
    4. Once you're happy, mint a new token without the group restriction
       and promote to the whole fleet.
  </Accordion>

  <Accordion title="Rotate the enrollment token">
    1. Mint a new token in **Endpoint → Devices**.
    2. Update the MDM payload to embed the new token. Existing
       devices are unaffected; rotation only matters for new
       enrollments.
    3. Revoke the previous token once your MDM has rolled the new
       payload to every staging point.
  </Accordion>

  <Accordion title="Replace a lost laptop">
    1. Revoke the device row in **Endpoint → Devices**.
    2. Ship the replacement with the same MDM policy as the rest of
       the fleet. The new device self‑enrolls and binds to the same
       directory user.
  </Accordion>

  <Accordion title="Roll the agent back off a group">
    See [Uninstalling the agent](/endpoint/uninstall), which covers the
    silent uninstall command, what it reverts, and what it destroys.
  </Accordion>
</AccordionGroup>
