---
title: "Scan API"
description: "Explicit endpoints for scanning prompts, responses, batches and agent tool calls. Two HTTP calls around your model give you the full firewall."
---

The Scan API is the explicit integration mode. You make one call
before sending a prompt to the model and one call after the response
comes back. Useful when you don't want to put a proxy in the chat
hot path, or when you're scanning text that isn't going to an LLM at
all (batch pipelines, document ingestion, knowledge‑base curation).

Every scan route is available at `/api/runtime-security/...` and at
`/api/v1/runtime-security/...`. They behave the same. Responses on a `/v1` path
carry the header `Blindsight-Api-Version: 1`. See
[API quickstart](/runtime-security/api-quickstart#versioned-paths).

All scan endpoints return **HTTP 200 with a JSON body even when the
verdict is `block`**. The verdict lives in the body so your code can
decide what to do. Non‑200 codes are reserved for protocol failures
(auth, rate limit, quota, an invalid request).

## Authentication

Send an [API key](/administration/api-keys) in the `X-API-Key` header. The
key needs the **Scan prompts and responses** permission (`runtime:scan`). A key
with **Full Runtime Access** (`runtime:*`) or full platform access also works.

To attribute traffic to an App, add `X-Blindsight-App-Id` with the App's UUID.
A key that is limited to one App uses that App without the header. A key that
is limited to several Apps must send it. If the workspace has exactly one App,
traffic is attributed to it when you omit the header.

| Status | When                                                                                   |
| ------ | -------------------------------------------------------------------------------------- |
| `401`  | The key is missing, invalid, expired, disabled or revoked (`INVALID_CREDENTIALS`). A key is revoked with its App when that App is archived or deleted. |
| `402`  | The workspace has used its request allowance for the current period (`QUOTA_EXCEEDED`). |
| `403`  | The key does not have the `runtime:scan` permission, or its owner no longer holds it. A key limited to other Apps gets `APP_NOT_ALLOWED`. |
| `404`  | Runtime Security (or, for tool calls, the agentic guardrails module) is not enabled for the workspace. |
| `413`  | A text is longer than one call can hold (`text_too_long`, also given as `legacy_code: PAYLOAD_TOO_LARGE`). See [Limits](#limits). The body says how long a part to send (`recommended_chunk_chars`). Nothing is scanned or counted. |
| `422`  | The request body is not valid (`VALIDATION_ERROR`). The error names the field and never repeats what you sent. Text that is not valid Unicode is refused the same way. |
| `409`  | `idempotency_key_reused`: the same `Idempotency-Key` was sent with a different body. Use a new key for a new body. |
| `429`  | You are over the rate limit (limits apply per API key), or requests are paced: `DAILY_ALLOWANCE_SOFT_LIMIT` when today's allowance is used, `plan_required` when the trial has ended or the plan is paused, `too_many_long_scans` when several long texts are being read at once. Wait `Retry-After` seconds and send the same request again. See [Plan and usage](/runtime-security/plan-and-usage). |
| `503`  | The firewall is disabled or still starting, the scanner could not be reached (`SCANNER_UNAVAILABLE`), or a long text could not be read to the end (`scan_incomplete`). Wait `Retry-After` seconds and send the same request again. A single prompt, reply or file scan that fails because the scanner could not run is not counted against your allowance. |

Every error answer carries the header `X-Blindsight-Error-Code`. Read the code
rather than the message. See [Errors](/runtime-security/errors).

## Limits

| Limit | Value |
| ----- | ----- |
| Text in one call | 250,000 characters for an App that does not block prompt injection, which is how a new API App starts. 32,000 characters for an App that does. |
| `/scan/restore` | Four times the limit of a call, because pseudonymised text can be longer than the original. |
| `/scan/file` | Files up to 5 MB, sent as base64 in a JSON body. |
| `/scan/batch` | 1 to 32 items. |
| Request body | 16 MiB. |

A text over the limit is answered with `413` and the code `text_too_long`. The
body carries `limit` and `recommended_chunk_chars`. Send the text in parts of
that size, or use the SDK, which splits a long document for you and numbers the
placeholders as one document. The answer carries `X-Blindsight-Error-Code:
text_too_long` and `Billable-Requests: 0`. This is the answer to a text of
250,001 characters, shortened:

```json
{
  "error": {
    "code": "text_too_long",
    "message": "This call holds 250001 characters. The limit is 250000 characters per call. Split the text into parts of at most 250000 characters, or use the SDK, which splits long documents for you.",
    "details": {
      "code": "text_too_long",
      "field": "text",
      "length": 250001,
      "scanned": false,
      "recommended_chunk_chars": 8000,
      "recommended_chunk_overlap_chars": 200,
      "limit": 250000,
      "legacy_code": "PAYLOAD_TOO_LARGE"
    }
  }
}
```

A text that repeats the people in it very often can be answered with `413` and
the code `too_many_name_repeats`. Nothing is returned and nothing is counted.
Split the text into parts of `recommended_chunk_chars`. The SDK does this for
you.

## Usage on every answer

Every scan answer says what the call used:

| Where | What |
| ----- | ---- |
| `Billable-Requests` header | The requests this call counted. See [Plan and usage](/runtime-security/plan-and-usage#what-a-request-is). |
| `usage` field | `billable_requests` and `characters`. A batch has `usage` on each result and a total. |
| `X-Blindsight-Text-Stored` header | `true` when text from the call is kept, `false` when it is not. You choose this per App. |
| `X-Blindsight-Usage-Plan-State` header | Where the workspace stands, for example `trial`. |
| `X-Blindsight-Usage-Month-Used`, `-Month-Included` and `-Month-Resets-At` headers | The requests used in the current period, the requests the plan includes and when the period ends (UTC). |

A call on a trial answers like this:

```text
Billable-Requests: 1
X-Blindsight-Usage-Plan-State: trial
X-Blindsight-Usage-Month-Used: 264
X-Blindsight-Usage-Month-Included: 10000
X-Blindsight-Usage-Month-Resets-At: 2026-12-10T17:35:01Z
X-Blindsight-Text-Stored: false
```

If your plan has a daily request allowance, every counted scan call made with an API
key also says how much of today's allowance is used, in the headers
`X-Blindsight-Usage-Day-Used`, `-Limit`, `-State` and `-Resets-At`, so you can
warn your team before requests are paced. Requests well past the allowance are slowed
down, never stopped for the day.

## `POST /api/runtime-security/scan/input`

Scan a user prompt before forwarding it to your LLM.

### Request

| Field           | Type   | Required | Notes                                                                       |
| --------------- | ------ | -------- | --------------------------------------------------------------------------- |
| `text`          | string | yes      | The prompt to scan. See [Limits](#limits).                                  |
| `session_id`    | string | no       | Your identifier for the conversation or agent run (up to 200 characters). Send the same value on every call of one run so related calls are judged together. For an App set to **Pseudonymize and restore**, it also keeps a value's placeholder the same in every turn, across `/scan/input`, `/scan/output` and `/scan/batch`. |
| `history`       | array  | no       | Up to 16 earlier turns of the conversation, oldest first. Each entry is a string or an object with `role` and `content`. |
| `untrusted`     | array  | no       | Up to 32 parts of the prompt that did not come from the user, such as retrieved documents. Each entry has `content`, and optionally `source` (`retrieval`, `tool_result`, `web`, `email`, `file`, `document`, `user_upload`, `other`) and `label`. |
| `source_app`    | string | no       | Free‑form app identifier (up to 128 chars). Diagnostic; not the App UUID.    |
| `provider`      | string | no       | `openai`, `anthropic`, `gemini`, `vertex`, `bedrock`, `groq`, and so on. Up to 32 chars. |
| `model`         | string | no       | Model name (up to 128 chars).                                                |
| `metadata`      | object | no       | Anything you want kept on the audit record.                                  |
| `custom_params` | object | no       | Typed key / value pairs declared by the resolved App.                        |

### Response

| Field           | Notes                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------- |
| `uuid`          | The event identifier. Empty when the workspace has event logging turned off.                 |
| `verdict`       | `allow`, `flag`, `redact` or `block`. See [Verdicts](/runtime-security/verdicts).            |
| `pii`           | `count` and `categories` of the personal data found.                                         |
| `redacted_text` | The text with personal data replaced by placeholders. Equal to the original when nothing was redacted. For an App set to **Mask**, a placeholder is a type marker such as `<EMAIL>`. For an App set to **Pseudonymize and restore**, it is numbered, such as `<PERSON_1>`. |
| `text_length`   | Length of the scanned text in characters.                                                    |
| `latency_ms`    | How long the scan took, in milliseconds.                                                     |
| `pseudonyms`    | Only for an App set to **Pseudonymize and restore**: each placeholder in `redacted_text` (for example `<PERSON_1>`) with the real value it stands for. It is in this response alone. Blindsight does not store it. |
| `usage`         | `billable_requests` and `characters` of this call. |
| `also_flagged`  | Only when the scan saw something its verdict does not say, for example `["prompt_injection"]` next to a `redact` on an App set to **Flag only**. Treat it like a `flag`. |

```bash
curl -X POST "https://platform.blindsight.io/api/runtime-security/scan/input" \
  -H "X-API-Key: $BLINDSIGHT_API_KEY" \
  -H "X-Blindsight-App-Id: <your app id>" \
  -H "Content-Type: application/json" \
  -d '{"text": "Please email the report to jane.doe@example.com", "session_id": "chat-8843"}'
```

The `X-Blindsight-App-Id` header is only needed when the key can use more than
one App. With a key that is limited to one App, leave it out.

```json
{
  "uuid": "<event uuid>",
  "verdict": "redact",
  "pii": {"count": 1, "categories": ["email_address"]},
  "redacted_text": "Please email the report to <EMAIL_ADDRESS_1>",
  "latency_ms": 199,
  "text_length": 47,
  "pseudonyms": {"<EMAIL_ADDRESS_1>": "jane.doe@example.com"},
  "usage": {"billable_requests": 1, "characters": 47}
}
```

This answer is for an App set to **Pseudonymize and restore**. An App set to
**Mask** answers with a type marker such as `<EMAIL_ADDRESS>` and has no
`pseudonyms`. `<event uuid>` stands for the identifier of the event.

The response carries further fields, among them `pii.findings` (where each item
sits in the text) and fields that describe how the scan reached its result. They
are left out of the examples on this page. Only the fields above are part of the
supported contract.

Rate limit: **200 requests per second per API key**.

```json
  "latency_ms": 49,
  "text_length": 44,
  "pseudonyms": {
    "<PERSON_1>": "Petra Hoffmann",
    "<PHONE_NUMBER_1>": "+41 79 555 01 02"
  },
  "usage": {"billable_requests": 1, "characters": 44}
}
```

Rate limit: **200 requests per second per API key**.

## `POST /api/runtime-security/scan/batch`

Scan up to 32 items in one call and save the HTTP overhead. Each item counts on
its own, at least one request, and the call's `usage` is the total.

### Request

| Field   | Type  | Required | Notes                     |
| ------- | ----- | -------- | ------------------------- |
| `items` | array | yes      | 1 to 32 items.            |
| `session_id` | string | no  | The conversation the items belong to. The items are numbered in order as one conversation, so a value keeps its placeholder across the items and across other calls with the same `session_id`. Without it every item is numbered on its own. |

Each item:

| Field        | Type   | Required | Notes                                                    |
| ------------ | ------ | -------- | -------------------------------------------------------- |
| `text`       | string | yes      | The text to scan.                                        |
| `direction`  | string | no       | `input` (default) or `output`.                           |
| `source_app` | string | no       | As above.                                                |
| `provider`   | string | no       | As above.                                                |
| `model`      | string | no       | As above.                                                |
| `metadata`   | object | no       | As above.                                                |

```bash
curl -X POST "https://platform.blindsight.io/api/runtime-security/scan/batch" \
  -H "X-API-Key: $BLINDSIGHT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "session_id": "chat-8844",
        "items": [
          {"text": "Please send the contract to Jonas Bergmann at jonas.bergmann@example.com", "direction": "input"},
          {"text": "Jonas Bergmann has the contract and will write from jonas.bergmann@example.com.", "direction": "output"}
        ]
      }'
```

### Response

`results` holds one entry per item, in the same order, with the same fields as
`/scan/input`. `usage` at the top is the total. The same person and e-mail
address have the same placeholder in both items, because both items carry the
same `session_id`.

```json
{
  "results": [
    {
      "uuid": "<event uuid>",
      "verdict": "redact",
      "pii": {"count": 2, "categories": ["email_address", "person"]},
      "redacted_text": "Please send the contract to <PERSON_1> at <EMAIL_ADDRESS_1>",
      "latency_ms": 57,
      "text_length": 72,
      "pseudonyms": {
        "<PERSON_1>": "Jonas Bergmann",
        "<EMAIL_ADDRESS_1>": "jonas.bergmann@example.com"
      },
      "usage": {"billable_requests": 1, "characters": 72}
    },
    {
      "uuid": "<event uuid>",
      "verdict": "redact",
      "pii": {"count": 2, "categories": ["email_address", "person"]},
      "redacted_text": "<PERSON_1> has the contract and will write from <EMAIL_ADDRESS_1>.",
      "latency_ms": 47,
      "text_length": 79,
      "pseudonyms": {
        "<PERSON_1>": "Jonas Bergmann",
        "<EMAIL_ADDRESS_1>": "jonas.bergmann@example.com"
      },
      "usage": {"billable_requests": 1, "characters": 79}
    }
  ],
  "usage": {"billable_requests": 2, "characters": 151}
}
```

The answer header `Billable-Requests` is `2`.

Rate limit: **40 requests per second per API key**.

A batch cannot be attributed to an App. A key that is limited to specific Apps
gets `400` with the code `APP_SCOPED_KEY`; use `/scan/input` and `/scan/output`
with `X-Blindsight-App-Id` for those keys.

## `POST /api/runtime-security/scan/tool-call`

Check an agent's tool call before you run it. This endpoint is part of the
agentic guardrails module; a workspace without it gets `404`.

### Request

| Field        | Type   | Required | Notes                                                                      |
| ------------ | ------ | -------- | -------------------------------------------------------------------------- |
| `tool_name`  | string | yes      | The tool being called (up to 200 characters).                              |
| `arguments`  | any    | no       | The arguments: an object, array, string or number. Defaults to `{}`.       |
| `session_id` | string | no       | As above.                                                                  |
| `source_app` | string | no       | As above.                                                                  |
| `provider`   | string | no       | As above.                                                                  |
| `model`      | string | no       | As above.                                                                  |
| `metadata`   | object | no       | As above.                                                                  |

### Response

| Field                | Notes                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------- |
| `uuid`               | The event identifier. Empty when event logging is off.                                 |
| `verdict`            | `allow`, `redact` or `block`.                                                          |
| `reasons`            | The rules that applied: a list of `code`, `severity` and `detail`. For example `tool.denied` when the tool is on the deny list, `tool.not_allowed` when an allow list exists and the tool is not on it, and `tool.args_too_large` when the arguments exceed the size limit. |
| `redacted_arguments` | The arguments with personal data masked. Use these when `verdict` is `redact`.         |
| `pii`                | `count` and `categories` of the personal data found in the arguments.                  |
| `arg_bytes`          | Size of the JSON‑serialised arguments in bytes.                                        |
| `latency_ms`         | How long the check took, in milliseconds.                                              |

```bash
curl -X POST "https://platform.blindsight.io/api/runtime-security/scan/tool-call" \
  -H "X-API-Key: $BLINDSIGHT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"tool_name": "send_email", "arguments": {"to": "jane.doe@example.com", "body": "Hello"}}'
```

```json
{
  "uuid": "e4a9c2b7-1f60-4d83-8a35-6b7c0d2e9f18",
  "verdict": "redact",
  "reasons": [],
  "redacted_arguments": {"to": "<EMAIL>", "body": "Hello"},
  "pii": {"count": 1, "categories": ["email"]},
  "arg_bytes": 52,
  "latency_ms": 3
}
```

Rate limit: **200 requests per second per API key**.

## `POST /api/runtime-security/scan/restore`

Put the real values back into text that carries placeholders. It does plain text
work on what you send: nothing is looked up, stored or logged.

| Field        | Type   | Required | Notes                                                       |
| ------------ | ------ | -------- | ----------------------------------------------------------- |
| `text`       | string | yes      | Text that carries placeholders.                              |
| `pseudonyms` | object | yes      | The mapping the scan response returned.                      |

The response holds `text` with the values back in and `restored`, how many of the
placeholders you sent were found in the text and put back (see the example in the
[API quickstart](/runtime-security/api-quickstart#put-the-values-back)). The original text comes back exactly as it was written. Restoring is free: it counts no requests. A text over the restore limit is refused with `413` and nothing is restored; so is a result that would be too large (`RESTORE_TOO_LARGE`). The official SDKs restore
locally, so they never need this route.

## Pseudonymisation and restore

For an App set to **Pseudonymize and restore**, each piece of personal data is
replaced, and you put the real values back in its answer. Personal names, email
addresses and phone numbers are replaced with realistic stand-ins, such as
`Maria Keller` or `maria.keller@example.com`. Every other type is replaced with a
numbered token such as `<IBAN_1>`, so one text can hold both. Your model works
with the replaced text.

The response says which kind it holds in `pseudonym_format`: `stand_in` when the
mapping holds at least one stand-in, `token` when it holds numbered tokens only.
Stand-ins are returned to callers that can restore them: the Python and
TypeScript SDKs from version 1.1, which say so with every request, or a request
that sets `"pseudonym_format": "stand_in"`. Any other caller gets numbered tokens,
and `"pseudonym_format": "token"` always does. If you call the API over plain HTTP
and ask for stand-ins, restore through `/scan/restore`. The examples below show
tokens.

- **The same value gets the same replacement.** Within one call, a value written
  twice has one placeholder. With a `session_id`, it keeps that placeholder in
  every later call of the conversation, and a new value gets the next number.
- **Names are replaced wherever they are written.** A person's name is replaced
  in every place it appears in the text, also when only the surname is written
  later ("Bergmann"). A title stays in the text ("Dr. <PERSON_1>"). A surname on
  its own gets a placeholder of its own, next to the one of the full name, and
  both are listed in `pseudonyms`, so restoring puts each back as it was written.
- **Restore is exact.** Put the values back with the `pseudonyms` mapping and you
  get the original text back, character for character. The SDKs restore
  locally. Without an SDK, use `/scan/restore`, described below. Restore through
  the SDK helper or `/scan/restore` rather than parsing the text yourself: it
  handles tokens and stand-ins in one pass.
- **The mapping is yours.** `pseudonyms` is in the response only. Its keys are
  the exact replacement strings as they appear in `redacted_text`, its values the
  originals. Blindsight does not keep it, and the text it stores for your events
  never holds a stand-in.

```json
{
  "text": "Dr. Jonas Bergmann signed on Monday. Later, Bergmann called again.",
  "session_id": "chat-8841"
}
```

```json
{
  "verdict": "redact",
  "redacted_text": "Dr. <PERSON_1> signed on Monday. Later, <PERSON_2> called again.",
  "pseudonyms": {"<PERSON_1>": "Jonas Bergmann", "<PERSON_2>": "Bergmann"}
}
```

A name that is written another way later in the text, for example split by a
line break or a double space ("Anna\nBergmann", "Anna  Bergmann"), gets its own
placeholder in the same family, such as `<PERSON_1_1>`, and `pseudonyms` lists
the exact characters written. In a call with a `session_id` the family also
carries the turn, such as `<PERSON_1_T1_1>`. Restoring puts back every form
exactly as it was written.

```json
{
  "redacted_text": "Vertrag mit <PERSON_1> geschlossen.\nDanach schrieb <PERSON_1_1> an uns.",
  "pseudonyms": {"<PERSON_1>": "Anna Bergmann", "<PERSON_1_1>": "Anna\nBergmann"}
}
```

### Restoring stand-ins

`/scan/restore` and the SDK helpers take the same mapping for both kinds. Every
key is replaced in one pass, longest first, and a restored value is never
expanded again. Only the keys of the mapping are restored. A stand-in name matches
on whole words in the case it was issued (and in capitals when it has four letters
or more), so an ordinary word is never touched; an English possessive or a German
genitive "s" right after it is tolerated ("Keller's", "Kellers"). Emails and phone
numbers match exactly. A stand-in inside anything that can be a link or a resource
is left as it is. The answer includes `unrestored`, a list of the stand-ins found
in such places. Treat a non-empty list as a warning: look at the text, or ask your
model again.

```json
{
  "text": "Maria Keller's invoice is ready. See https://example.com/Keller",
  "pseudonyms": {"Maria Keller": "Jonas Bergmann", "Keller": "Bergmann"}
}
```

```json
{
  "text": "Jonas Bergmann's invoice is ready. See https://example.com/Keller",
  "restored": 1,
  "unrestored": ["Keller"]
}
```

Use SDK version 1.1 or later for stand-ins. Version 1.0 only understands numbered
tokens, which is why it keeps getting them.

An App set to **Mask** replaces each piece with a type marker such as
`<PERSON>` instead, and has no `pseudonyms` and no restore.

## Files

`POST /api/runtime-security/scan/file` scans a file and returns it redacted.

| Field | Type | Required | Notes |
| ----- | ---- | -------- | ----- |
| `data` | string | yes | The file, base64 encoded. Up to 5 MB. |
| `filename` | string | no | The file name. |
| `media_type` | string | no | For example `application/pdf`. Detected when you omit it. |
| `direction` | string | no | `input` (default) or `output`. |

Formats: PDF, Word (`docx`), Excel (`xlsx`, `xls`), `csv`, `txt`, `md`, `json`
and images.

```bash
curl -X POST "https://platform.blindsight.io/api/runtime-security/scan/file" \
  -H "X-API-Key: $BLINDSIGHT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "data": "TWVldGluZyBub3RlcwpQbGVhc2Ugc2VuZCB0aGUgY29udHJhY3QgdG8gRHIuIEpvbmFzIEJlcmdtYW5uIGF0IGpvbmFzLmJlcmdtYW5uQGV4YW1wbGUuY29tLgo=",
        "filename": "notes.txt",
        "media_type": "text/plain",
        "direction": "input"
      }'
```

`data` is the text `Meeting notes`, a line break, and `Please send the contract to Dr. Jonas Bergmann at jonas.bergmann@example.com.`, base64 encoded.

```json
{
  "uuid": "<event uuid>",
  "verdict": "redact",
  "pii": {"count": 2, "categories": ["email_address", "person"]},
  "redacted": true,
  "redacted_count": 2,
  "data": "TWVldGluZyBub3RlcwpQbGVhc2Ugc2VuZCB0aGUgY29udHJhY3QgdG8gRHIuIDxQRVJTT04+IGF0IDxFTUFJTF9BRERSRVNTPi4K",
  "media_type": "text/plain",
  "filename": "notes.txt",
  "kind": "text",
  "extracted_chars": 91,
  "latency_ms": 54
}
```

`data` in the answer is the redacted file, base64 encoded. Decoded, it reads
`Please send the contract to Dr. <PERSON> at <EMAIL_ADDRESS>.` under the first
line. The answer carries `Billable-Requests: 1`.

The answer holds `verdict`, `pii`, `redacted` and `redacted_count`, and `data`,
the file with personal data replaced by type placeholders such as `<PERSON>`
and `<EMAIL_ADDRESS>`. It also names the file (`filename`, `media_type`, `kind`)
and says how much text was read (`extracted_chars`). A file scan returns type
placeholders and has no `pseudonyms` mapping, so there is nothing to restore.
The extracted text counts as requests like any text. Rate limit: **60 requests
per second per API key**.

## Retries and idempotency

Send an `Idempotency-Key` header (up to 255 characters) to make a retry safe.
The same key with the same body within 24 hours is not counted again. The
answer carries `Billable-Requests: 0` and `Idempotent-Replay: true`. The key
guards retries: send a new key for each new text. The same key with a different
body is answered with `409` and the code `idempotency_key_reused`.

## Protect a chatbot

For a chatbot, set the App to **Pseudonymize and restore**, create a scan key
limited to that App, and make two calls around your model. Your model sees
placeholders, never the real values, and your user gets their own values back.

1. Call `/scan/input` with the user's message and a `session_id`. On `block`,
   answer with a refusal and stop. Otherwise keep `pseudonyms` and send
   `redacted_text` to your model.
2. Call `/scan/output` with the model's reply, the text your model saw as `prompt`,
   and the same `session_id`. On `block`, answer with a refusal.
3. Replace each placeholder listed in the second call's `pseudonyms` with a word
   such as `[hidden]`. That is personal data the model wrote on its own, and it
   stays hidden.
4. Put the user's values back with the first call's `pseudonyms`.

Create the `session_id` on your server, one random value per conversation. Never
use a value your users can choose or see. Within a conversation a value keeps its
placeholder in every message and a new value gets the next number, so you can give
your model the earlier turns. Keep one list of placeholders per conversation, add
each call's `pseudonyms` to it, and never log it or your users' messages.

| You get                                      | Do this                                                              |
| -------------------------------------------- | -------------------------------------------------------------------- |
| `allow`                                      | Carry on.                                                            |
| `redact`                                     | Carry on with `redacted_text`, and put the values back at the end.   |
| `flag`, or an `also_flagged` list            | Carry on, and note the event `uuid` so someone can review it.        |
| `block`                                      | Do not use the text. Answer with a refusal.                          |
| `401` or `403`                               | The key is wrong, revoked or not allowed for this App. Fix the configuration and do not retry. |
| `429` with `DAILY_ALLOWANCE_SOFT_LIMIT`      | Wait `Retry-After` seconds, then send the same request again.        |
| Timeout, `503` or any other error            | Answer that the service is unavailable. Do not answer around it.     |

Answering without protection when Blindsight cannot be reached sends your users'
text, personal data included, to your model unscanned. If you choose it, limit it to
Blindsight being unreachable, never to a slow or refused request, which a user can
cause on purpose. Use a timeout of about ten seconds. Every message makes two
calls, one before the model and one after, and each counts requests by its
length.

The SDKs wrap this. They read the error code and the wait from a response, retry a
`429` or `503` a bounded number of times and honour `Retry-After`, and they raise an
error you handle rather than letting text through unscanned. Both SDKs are
Apache-2.0.

## Wrapping it around your model

The minimal integration: scan input, call your model, scan output.

```python
import httpx

BLINDSIGHT = httpx.Client(
    base_url="https://platform.blindsight.io",
    headers={
        "X-API-Key": "ak_...",
        "X-Blindsight-App-Id": "<your app id>",
    },
    timeout=10.0,
)

def safe_chat(user_text: str) -> str:
    # Pre-flight
    pre = BLINDSIGHT.post(
        "/api/runtime-security/scan/input",
        json={"text": user_text},
    )
    pre.raise_for_status()
    v = pre.json()
    if v["verdict"] == "block":
        raise PermissionError(f"Blocked (event: {v['uuid']})")
    # "flag" and "allow" both fall through here: flag is a recording
    # verdict, redacted_text is unchanged from the original for it.
    safe_text = v["redacted_text"] if v["verdict"] == "redact" else user_text

    # Your model
    response = call_my_llm(safe_text)

    # Post-flight
    post = BLINDSIGHT.post(
        "/api/runtime-security/scan/output",
        json={"prompt": safe_text, "response": response},
    )
    post.raise_for_status()
    o = post.json()
    if o["verdict"] == "block":
        return f"I can't share that. (event: {o['uuid']})"
    return o["redacted_text"] if o["verdict"] == "redact" else response
```

LangChain, and LlamaIndex variants.

## When to prefer the Scan API over the proxy

- You don't want the firewall in the chat request path.
- You're scanning text that isn't going to an LLM at all.
- You're processing a large batch (`/scan/batch` is the right tool).
- You're wiring custom middleware in a language without a maintained
  OpenAI / Anthropic SDK.

For chat traffic that does go to a standard SDK, the
[reverse proxy](/runtime-security/reverse-proxy) is faster to set up
and harder to bypass.
