---
title: "Verdicts"
description: "What `allow`, `flag`, `redact`, and `block` mean, and how to act on each."
---

Every scan call returns one of four verdicts. Your integration reads the
verdict and acts on it.

## The four values

| Verdict   | What it means                                                              | What your application should do                                                                                    |
| --------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `allow`   | Nothing of concern was found.                                               | Forward the original text untouched.                                                                                |
| `flag`    | Something looks suspicious, but Blindsight did not act on it.               | Forward the original text unchanged (nothing is masked). Treat it as a signal to review, not to block on.          |
| `redact`  | Personal data or a secret was found.                                        | Use `redacted_text` (or `redacted_arguments` for tool calls) instead of the original. Sensitive values become `<CATEGORY>` markers. |
| `block`   | The content should not be sent.                                             | Refuse the request. Show your end user a generic refusal and log the `uuid` for correlation.                       |

<Note>
  `flag` passes content through **unmodified**. It is a recording verdict,
  not an enforcement one: it lets you see suspicion without changing or
  blocking traffic. Watch `flag` volume in
  [Observability](/runtime-security/observability). A sustained rise is a
  cue to review the events and, if the pattern is real, make the App's
  settings stricter.
</Note>

## Settings that shape the verdicts

How readily an App returns `redact` or `block` is controlled by its
sensitivity settings, one pair for input traffic and one pair for output
traffic. A stricter setting returns more `redact` and `block` verdicts and
more false alarms. A more lenient setting returns fewer of both. See
[Configuration](/runtime-security/configuration) for how to change them.

<Tip>
  By default, a classifier that fails at runtime lets the remaining checks
  decide. Set `RUNTIME_SECURITY_FAIL_MODE=closed` (a workspace-level
  environment variable) to force `block` instead. See
  [Errors & FAQ](/runtime-security/errors) for fail-closed behaviour.
</Tip>

## Acting on each verdict

### On `allow`

Forward the original text. There is nothing to do. The `uuid` is still
useful to log if you want to correlate dashboards back to specific user
requests.

### On `flag`

Forward the original text: `flag` never rewrites anything. Log it and treat
it as a lead. Filter the event log to `verdict=flag` to see what is
suspected but not acted on. It is a deliberate "do not act on this alone"
signal, not a bug in your integration.

### On `redact`

Use `redacted_text` for inputs and outputs, or `redacted_arguments` for tool
calls. Sensitive values are replaced with category markers:

```
my email is <EMAIL> please reply
```

The categories cover structured secrets such as `EMAIL`, `PHONE`, `SSN`,
`IP`, `URL`, `API_KEY`, `JWT`, cloud and source-host credentials, private
keys and bearer tokens, the [national identifiers](#national-identifiers)
below, and any custom categories you defined as App-level or workspace-level
rules. When [NER PII detection](/runtime-security/configuration#ner-pii-detection)
is enabled in `redact` mode, unstructured categories such as `PERSON`,
`ADDRESS`, `DATE_OF_BIRTH` and `MEDICAL_CONDITION` are masked too, along
with any custom label you configured.

### National identifiers

Government-issued identifiers are recognised and masked when they check out
against the structure the issuing authority uses.

| Identifier                                              |
| -------------------------------------------------------- |
| Swiss AHV / AVS social security number                    |
| UK NHS number                                             |
| German tax identification number (Steuer-IdNr)            |
| Swiss vehicle registration plate                          |

### On `block`

Do not forward anything to the upstream model. Show your end user a
refusal that does not describe why the content was blocked.

Log the `uuid`. The same UUID appears on the audit event, so you can pull it
up in the Blindsight dashboard when investigating.

## Why `block` returns HTTP 200

The verdict is information your application needs. Returning 200 with
`verdict` and `uuid` keeps the contract clean. Non-200 codes are reserved
for protocol failures (auth, rate limit, quota) where the client cannot
retrieve a verdict.

## What `redacted_text` looks like

| Original                                              | Redacted                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------ |
| `email me at jane@example.com about case INC-1234`    | `email me at <EMAIL> about case <CUSTOM:incident_id>`               |
| `here is my AWS key AKIAIOSFODNN7EXAMPLE`              | `here is my AWS key <AWS_ACCESS_KEY>`                               |
| `Maria Fernandes, born 12 March 1989, maria.f@example.com` (with NER `mode="redact"`) | `<PERSON>, born <DATE_OF_BIRTH>, <EMAIL>` |

On `verdict: allow`, `redacted_text` equals the original. On `block`, do not
forward `redacted_text` either. The content should not reach the model.

## Tuning sensitivity

Start with the defaults. Change them only when you have data from your own
traffic.

<AccordionGroup>
  <Accordion title="Too many false alarms">
    Make the App's settings more lenient in small steps, and watch the
    verdict mix shift on the [analytics](/runtime-security/observability)
    page after each change.
  </Accordion>

  <Accordion title="Too little is being caught">
    Make the redaction setting stricter first. That turns borderline
    `allow`s into `redact`s without refusing user requests. Make the block
    setting stricter only once you trust the redaction one.
  </Accordion>

  <Accordion title="Different posture per surface">
    Do not change workspace settings. Create a new App and put the
    sensitive surface there. The healthcare template ships with a stricter
    posture, so clone it for any PHI workload.
  </Accordion>
</AccordionGroup>
